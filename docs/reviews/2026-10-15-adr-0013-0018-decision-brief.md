## 3. Verifying `CLIENT_IP_FORWARDING_TOKEN` (task 1)

Not verifiable from Claude's environment: its network policy blocks `*.vercel.app` and `*.onrender.com`, and Claude did not route around it. In any case, the forwarding code is only on the PR #14 branch, so the deployed services do not use the secret yet.

Safe check after PR #14 is merged and deployed, without real accounts and without exposing the secret:
1. Use a made-up email (for example `lockout-test-1@example.test`). From network A (say, home Wi-Fi), make 6 wrong sign-in attempts. The 6th should say "too many attempts".
2. From network B (say, a phone on mobile data), sign in with a **different** made-up email. You should get the normal "incorrect password" message, not "too many attempts". That proves visitors are no longer in one shared bucket.
3. Optionally, in the Render API logs, confirm no secret value appears (logs record only generic codes).

If step 2 says "too many attempts", the secret is missing or different on one of the services, or the deployment is not on the PR #14 code.
