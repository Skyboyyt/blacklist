The frontend talks to seven interfaces (`AdminApi` added by the Phase 5 follow-up). Replacing the mock adapter with an HTTP adapter must not change any component. **The mock services are reference behaviour, not authorization**: every rule below must be enforced by the API, server-side, at route and domain level (AGENTS §7).

## 1. Conventions the adapter maps

### Phase8 public research adapter (2026-10-14, local review only)

The non-mock server client implements `getViewer`, explicit-network `search`, address and transaction research using `/api/internal/v1` and the existing trusted peer/internal/staging gates. Optional typed `getAddressHistory`, `getTokenResearch`, `getContractResearch`, and `getTokenBalances` expose only capability-ready public chain DTOs, not invented mock responses. GET/HEAD equivalents under `/api/v1` are public chain reads with existing staging ingress and abuse controls; no actor's private activity is returned or recorded. Failed/malformed/unconfigured reads remain provider-unavailable, never `not_found` or successful empty lists. New `chain-reads.ts` DTOs contain snapshot/finality/freshness/coverage; unavailable address sections cannot carry findings or risk verdicts. History cursors bind provider/network/address/direction/page size/snapshot and are encrypted/authenticated, not page-number translation.

| Route suffix (both prefixes)                 | Policy / validation                                                                                                                                                                                                                                                 | Public output                                                                                                                                               |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/search`                                    | Public or internal GET/HEAD; strict `searchRequestSchema`. A chosen network is honoured; without one the API classifies the input on each network (one match is searched, a value valid on both returns `choose_network`, none is `invalid_identifier`; 2026-10-17) | Existing `searchResponseSchema`, chain-only hits, no computed band                                                                                          |
| `/addresses/:chain/:identifier`              | Public or internal GET/HEAD; chain enum, family checksum/Base58 validation, bounded options                                                                                                                                                                         | `researchResultSchema(addressResearchSchema)`; assessment/publication sections explicitly unavailable                                                       |
| `/transactions/:chain/:identifier`           | Same; family hash/signature validation                                                                                                                                                                                                                              | `researchResultSchema(transactionResearchSchema)`; real status/fees and separate transfer evidence/authorization                                            |
| `/addresses/:chain/:identifier/transactions` | Same; bounded1–100 limit, scoped cursor, direction; Ethereum provider max25/in-or-out                                                                                                                                                                               | `researchResultSchema(addressHistorySchema)`; incomplete coverage, optional failover restart                                                                |
| `/addresses/:chain/:identifier/token`        | Same; bounded finality/verify options                                                                                                                                                                                                                               | `researchResultSchema(tokenResearchSchema)`; untrusted on-chain text, raw integer supply                                                                    |
| `/addresses/:chain/:identifier/contract`     | Same                                                                                                                                                                                                                                                                | `researchResultSchema(contractResearchSchema)`; bytecode hash, explorer verification unknown                                                                |
| `/addresses/:chain/:identifier/balances`     | Same                                                                                                                                                                                                                                                                | `researchResultSchema(tokenBalancesSchema)`; classic SPL supported; separately gated Ethereum discovery plus same-block calls, bounded/incomplete inventory |

Unknown fields never become output; no provider ID/key/URL, account/session, private submission, numeric score or unreviewed allegation appears. API route matrix includes both prefixes and methods; negative ingress/private/input/rate/persistence tests are in `research.integration.test.ts`. The preserved project-directory pagination decision below remains open; no live project/catalog/ranking adapter is introduced. Live dashboard uses an honest search/account fallback; reports/projects/scoreboard unavailable states cannot confer submission or publication success. Supported mock journeys remain unchanged. See [operations](../operations/phase8-research.md) and the [report](../reviews/2026-10-14-phase8-implementation.md).

| Topic            | API (ARCHITECTURE §7.1, §7.3)                                                                                      | Frontend result type                                                                                                                             |
| ---------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Transport        | REST + JSON under `/api/v1`, cookie session, exact-Origin check on every mutation, `no-store` on private responses | Adapter-internal                                                                                                                                 |
| Validation       | Zod schemas from `@blacklist/contracts` at the API boundary; unknown fields stripped or rejected (strict objects)  | The same schemas validate forms (UX only)                                                                                                        |
| Errors           | RFC 9457 problem details with a stable `code`                                                                      | Discriminated results: `MemberResult`, `ModerationResult`, `ResearchResult`, `AccountActionResult`. Mapping in §6                                |
| Hidden existence | Inaccessible private resources return 404                                                                          | `not_found` (never "forbidden" for someone else's submission)                                                                                    |
| Concurrency      | Every mutation of a case or submission carries `expectedVersion`; mismatch → 409                                   | `conflict` with a reason; the UI offers "Load the latest version/status" and never retries silently                                              |
| Idempotency      | Creation endpoints accept an `Idempotency-Key` header                                                              | The HTTP adapter (Phase 7) must send one per form submission so a retry cannot create two submissions; today the forms only block double submits |
| Dates and IDs    | ISO-8601 UTC; UUIDv7 IDs; on-chain integers as decimal strings                                                     | Displayed IDs (`RPT-…`) are mock conveniences; the UI treats IDs as opaque strings                                                               |

**Pagination — open integration decision.** ARCHITECTURE §7.1 specifies cursor pagination (max 100). The Phase 3–4 contracts use page numbers (`page`, `totalPages`; directory 6 per page, queue 8 per page) because the directory and queue show "Page N of M" and keep the page in the URL. Before Phase 7 either (a) the API offers offset pages for these two bounded, staff-curated lists, or (b) the contracts and UI move to cursors with previous/next only. Recommendation: (a) for the directory and queue (small, bounded), cursors elsewhere. Either choice is recorded in ARCHITECTURE §7.1.

**Standing by subject** (moderation §6.2): a control signature for wallets and unknown addresses, an authority signature (owner, admin, upgrade or mint authority, deployer, plus a finalized chain read) for contracts and tokens, DNS TXT on one of the profile's official domains for projects, documents for anyone. The service refuses a mismatch; the UI offers only the fitting mechanisms.

**Transitions the member can cause** (moderation §9–§10, ADR 0010 Part A):

| Kind               | Member action                         | From → to                                                                                                    |
| ------------------ | ------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Report             | submit                                | `draft → submitted` (screening and queueing are worker steps)                                                |
| Report             | reply                                 | `needs_info → in_review`                                                                                     |
| Report             | withdraw                              | any status before a decision → `withdrawn`                                                                   |
| Project suggestion | reply                                 | `needs_information → submitted`                                                                              |
| Appeal             | reply after denied standing           | standing `denied → pending` (status unchanged)                                                               |
| Appeal             | withdraw                              | `submitted`, `in_review` → `withdrawn`; "under appeal" ends only when no other appeal on the finding is open |
| Correction         | —                                     | No member transitions after submission (status set is a documentation gap: §9)                               |
| Response           | reply after denied standing; withdraw | standing `denied → pending`; `submitted`, `in_review` → `withdrawn`                                          |

**What the member view must never contain:** internal notes, internal rationales, staff identities or handles, other submitters, duplicate signals, screening flags, evidence state beyond "received". `memberSubmissionDetailSchema` is strict, so the API cannot add them by accident.

**Server check order for `decide`** (the mock implements exactly this): staff + assurance → scope → permission (ARCHITECTURE §9.2; `project:manage` for accepting corrections and suggestions; `standing:decide` for standing) → `expectedVersion` → allowed transition for type and status → assignment (only the assigned reviewer decides; `start_review` assigns) → independence (appeal participants refused for standing and appeal decisions; severe and severe-replacement approvals need an independent non-author; a replacement approver must also be a non-participant of the current public revision) → step-up grant for consequential decisions.

**Transitions** (moderation §9–§10, ADR 0010 Part A):

| Type               | Transitions                                                                                                                                                                                                                                                                                                                                                                                                                                                     | Step-up                           |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| Report             | `queued → in_review`; `in_review → needs_info / accepted / rejected / rejected_abusive`                                                                                                                                                                                                                                                                                                                                                                         | accept, reject, reject as abusive |
| Appeal             | `submitted → in_review`; while `in_review`: pending standing → granted / denied; with standing granted → `upheld / amended / reversed`. `amend` carries the new severity and public summary and creates a new finding revision authored by the reviewer (`sourceCaseId` = the appeal); nothing public changes until that exact revision is approved under §4.1, and the amended text never appears in the public timeline before approval (moderation §8.1, §9) | uphold, amend, reverse            |
| Correction         | `submitted → in_review → accepted / rejected`                                                                                                                                                                                                                                                                                                                                                                                                                   | accept, reject                    |
| Project suggestion | `submitted → needs_information / accepted_into_profile / not_accepted`                                                                                                                                                                                                                                                                                                                                                                                          | accept, do not accept             |

| Suspension review  | `open → reinstated / reversed` (`finding:publish`); reviewer is not the finding's author or approver; a severe finding cannot be reversed by its suspender                                                                                                                                                                                                                                                                                                      | reinstate, reverse                |

**Effects the API performs in the same transaction** (the mock's `public-effects.ts` is the reference): `accept_report` creates a finding revision (never a publication); an approval is blocked during an unresolved emergency suspension, creates a minimal record for a new subject without inventing chain facts, publishes that exact revision and recomputes the assessment with the active ruleset; an appeal filing sets the derived "under appeal" state (never replacing "suspended"); `reverse` removes the finding and its risk factor from the current assessment (history is preserved, append-only); `accept_correction` first checks the proposal’s base profile revision and then creates a new project profile revision; `accept_suggestion` creates a staff project profile and links it; a suspension hides the finding text (public page shows only "Temporarily suspended pending review"), retracts its signal and produces a new assessment, and reinstatement or reversal undoes or finalizes that; `publish_response` publishes the plain-text body with the standing mechanism and date; every decision appends audit rows and enqueues the submitter notification (§6).

## 8. Mock boundaries (what is simulated today)

- All data is fictional and lives in an in-memory store per demo session on the Next server (mock builds only). It is lost on restart; "Reset demo data" restores the fixtures.
- Roles, the passkey result and the session are mock cookies anyone can change: **the permission demonstrations are not production authorization.**
- Evidence: metadata only; nothing uploaded, scanned or previewed. Signature, authority-signature and DNS standing: simulated and labelled `SIMULATED`; no chain read or DNS lookup happens.
- Administrator console: staff, members and emails are fictional (`example.test`); the enrollment code is a fictional `DEMO…` value; no invitation email is sent; a second administrator is the `admin_b` preview viewer; the 24-hour recovery window cannot elapse in a demo session. Chain data: fixtures; no provider calls. Email: none.
- `POST /api/mock/rpc` exists only in mock builds (404 otherwise) and is replaced by the HTTP adapter in Phase 7; it must never be deployed as an API.

## Review repair notes (2026-10-13)

The mock `verifyStepUp` parameters are the exact mutation's argument array (including the target ID where the method takes it): e.g. `[findingId, revisionNumber, contentHash]` for approval and `[caseId, expectedVersion, decision]` for case decisions. The UI binds the confirmed parameters; omitting or changing them fails closed. Staff role changes, suspension, offboarding and recovery invalidate outstanding mock grants. This is a demonstration of the approved protocol, not real WebAuthn.

Standing eligibility is checked in the service as well as the UI: DNS never proves standing for an address, and a project DNS proof must match an official domain. Profile corrections conflict when the live profile revision differs from the reviewed proposal's base. Existing participant history is retained for subsequent appeal/standing independence checks.
