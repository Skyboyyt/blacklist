## Order matters

1. Merge the PR.
2. Apply this script (Steps 1–4).
3. Deploy the Render API, then the worker. Vercel needs nothing for this slice.

The new code writes risk rows whenever a finding is published, suspended, reinstated or reversed. Deploying it before the tables exist would make those moderation actions fail.

## What it changes and why it is safe

- **Adds 9 empty tables.** No existing table is changed.
- Runtime grants match the repository runner:
  - read and write on `risk_rulesets`, `risk_signals`, `risk_subject_state` and `current_risk_assessments`;
  - **SELECT and INSERT only** on the five history tables (`risk_signal_revisions`, `risk_assessments`, `risk_assessment_inputs`, `risk_assessment_factors`, `assessment_annotations`), which also reject UPDATE and DELETE by trigger.
- Public risk bands stay hidden: `RISK_PUBLIC_BANDS` defaults to `false` (owner decision O-12).
- Atomic and runs as `blacklist_migrator`: any error changes nothing.

**Rehearsal (2026-10-17, disposable PostgreSQL 18):** 14 entries were applied by the repository runner from `main` (`79f0cc8`), then the script was run as an owner role with ADMIN but no SET on the migrator (as on Neon).

## After deploying

Assessments appear the next time a finding is published, suspended, reinstated or reversed. Findings published before this migration have no assessment until then. Staff see the score in the case view, and the public page keeps saying "not assessed" until `RISK_PUBLIC_BANDS=true` is set on the API (after O-12).
